# API Error Handling Specification
**Version:** 1.0.0  
**Status:** Approved  
**Prepared By:** Rachana Gandla  

This document outlines the standard error formats, HTTP status code conventions, and exception handling policies for the DevTrack REST APIs (under `/api/v1`).

---

## 1. Standard Error Response Format

To ensure consistent integration for all frontend clients, every error returned by the DevTrack API will conform to a unified JSON structure:

```json
{
  "error": {
    "code": "STRING_ERROR_CODE",
    "message": "User-friendly description of the error.",
    "request_id": "unique-request-uuid-from-logger",
    "details": [
      {
        "field": "name_of_field_causing_error",
        "issue": "Specific explanation of field validation issue."
      }
    ]
  }
}
```

### Response Fields
*   `code`: A distinct uppercase string tag identifying the category of error. This should be used by client applications to trigger custom UI handling.
*   `message`: A human-readable message describing the error.
*   `request_id`: A unique trace ID generated by the structured logging middleware. This ID helps developers query server-side logs during investigations.
*   `details`: (Optional) An array of validation issues, primarily used for form-field rejection (e.g. invalid email syntax).

---

## 2. HTTP Status Code Conventions

DevTrack APIs map exceptions to standard HTTP response codes according to their business meaning:

| Status Code | Error Code | Scenario |
| :--- | :--- | :--- |
| **`400 Bad Request`** | `VALIDATION_ERROR`, `INVALID_OPERATION` | Invalid parameter values, malformed JSON bodies, or trying to perform an invalid transition. |
| **`401 Unauthorized`** | `AUTHENTICATION_FAILED`, `TOKEN_EXPIRED` | Accessing secure resources without a token, with an expired token, or providing invalid login credentials. |
| **`403 Forbidden`** | `PERMISSION_DENIED` | Valid credentials provided, but the user is not authorized to read/modify this resource. |
| **`404 Not Found`** | `RESOURCE_NOT_FOUND` | Querying a profile, dashboard data, or report that does not exist. |
| **`422 Unprocessable Entity`** | `SCHEMA_VALIDATION_ERROR` | Request payload fails Pydantic schema validation. |
| **`429 Too Many Requests`** | `RATE_LIMIT_EXCEEDED` | Client has made too many requests in a short time. |
| **`500 Internal Server Error`** | `INTERNAL_SERVER_ERROR` | An unhandled exception occurred within the database connection, sync queue, or parser engines. |

## 3. Exception Mapping in FastAPI

Every API router will utilize a global exception handler middleware to catch raw Python exceptions and map them to our standard format.

### 3.1 Example Pydantic validation mapping
```python
# Conceptual middleware wrapper mapping FastAPI's default 422 to 400 with details
from fastapi import Request, status
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError

async def validation_exception_handler(request: Request, exc: RequestValidationError):
    details = []
    for error in exc.errors():
        details.append({
            "field": ".".join(map(str, error["loc"][1:])),
            "issue": error["msg"]
        })
    
    return JSONResponse(
        status_code=status.HTTP_400_BAD_REQUEST,
        content={
            "error": {
                "code": "VALIDATION_ERROR",
                "message": "Input validation failed.",
                "request_id": request.state.request_id,
                "details": details
            }
        }
    )
```

### 3.2 Handling Uncaught Exceptions
If a database connection fails or a third-party parser throws an unexpected error:
*   The middleware logs the full stack trace with the `request_id`.
*   The client is returned a clean `500 Internal Server Error` status with the code `INTERNAL_SERVER_ERROR`.
*   **Production Security:** The raw stack trace is *never* sent in the API response to avoid exposing database names or server file paths.
